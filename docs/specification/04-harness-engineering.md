# Часть IV. Harness Engineering

## 1. Главный принцип

Агенты не изобретают архитектуру по ходу задачи. Репозиторий — единственный источник истины. Сначала инструкции и контекст, потом код.

## 2. Корневые файлы

`AGENTS.md`, `README.md`, `CONTRIBUTING.md`, `CHANGELOG.md`.

## 3. Cursor Rules

`.cursor/rules/00` … `10` — короткие применимые правила со ссылками на docs, без копирования всей документации.

## 4. Документация и ADR

`docs/*` + `docs/decisions/ADR-0001…0007`. Существенные архитектурные изменения фиксируются ADR.

## 5. Роли агентов

01 Product Architect · 02 Frontend Engineer · 03 Design System Engineer · 04 Visual Researcher · 05 Content Architect · 06 Prompt Engineer · 07 QA Engineer · 08 Security & Release Reviewer.

Один агент — одна зона ответственности. Не плодить роли ради количества.

## 6. Skills

Библиотека в `.agents/skills/` с воспроизводимыми процедурами. Обязательные секции SKILL.md: название, назначение, когда применять/не применять, входы, шаги, результат, проверки, запреты, примеры, связанные документы.

Дополнительно: skill проверки результата coding-агента по экспортированному `DESIGN.md`.

## 7. Контекстная дисциплина

Не грузить все документы в каждый запрос. Агент отчитывается: что изучил, изменил, решил, проверил, что осталось.

## 8. Запреты

Менять философию без согласования; менять архитектуру без ADR; зависимости без обоснования; дубли компонентов; фиктивные данные; `any` без нужды; suppress lint; обход/удаление тестов; декоративная подмена функциональности; массовый reformat; ломать published styles без совместимости.

## 9. CI Quality Gates

TypeScript, ESLint, unit tests, content schema validation, build, E2E smoke, secret scan, export integrity. Для визуальных изменений — screenshot tests.

## 10–14. DoD, цикл, git, память

`PLAN → IMPLEMENT → TEST → REVIEW → DOCUMENT → ACCEPT`  
Ветки: `main`, `feature/*`, `fix/*`, `docs/*`. Один логический результат — один PR. Память проекта только в репозитории.
